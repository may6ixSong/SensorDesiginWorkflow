# [프롬프트] A Tier 연동 서비스 — recipient 정책 변경 대응 요청

> **용도** — SIREN v3 개정으로 A Tier 산출물의 열람·선택 규칙이 바뀌었다. 이 문서는 A Tier로
> 연동된(또는 연동 예정인) 각 산출물 서비스 담당자/개발 세션에 **그대로 전달**하기 위한 요청문이다.
> 계약 원문은 `docs/observer-contract-v1.yaml` 이며, 이 문서는 그 계약에 **무엇이 추가로
> 요구되는지**만 설명한다.

---

## 0. 배경 — SIREN 쪽에서 무엇이 바뀌었나

SIREN에 **recipient(수신 대상)** 개념이 새로 생겼다.

- SIREN의 workflow는 자기 산출물들을 **부서 단위로 release(전달)** 한다.
- 산출물마다 "이걸 받을 부서/사용자"가 정해져 있다.
- **B/C/D Tier**는 SIREN이 권한을 직접 들고 있으므로, view 권한 목록이 곧 recipient다.
- **A Tier**는 권한을 그 서비스가 관리한다. 그래서 SIREN은 권한에 관여하지 않고,
  **알림을 받을 recipient만 따로 보관**한다.

여기까지는 서비스 쪽에 아무 영향이 없다. 문제는 다음 두 가지다.

---

## 1. 요청 ①: `access` 엔드포인트가 반드시 필요하다

### 무엇이 필요한가

계약의 **선택 항목이던 `access` 엔드포인트를 필수로 승격**한다.

```
GET /artifacts/{artifactId}/access?knoxId={knoxId}

200 OK
{
  "canView": true,
  "canEdit": false,
  "editors": ["knox.id.1", "knox.id.2"]     // canEdit 인 호출자에게만. 없으면 생략 가능
}
```

### 왜 필요한가

SIREN에서 **"다른 workflow가 만든 산출물을 내 캔버스에 받아오는"** 기능을 만든다. 이때 후보
목록에 올릴 수 있는 A Tier 산출물은 **"그 서비스에서 내가 view 권한을 가진 것"** 뿐이다.
SIREN은 그 판정을 할 수 없으므로 서비스에 물어봐야 한다.

- SIREN은 후보 목록을 만들 때 서비스별로 **병렬 조회**한다.
- 응답이 느리거나 실패하면 SIREN은 그 서비스의 산출물을 후보에서 빼고
  "일부 서비스를 조회하지 못했습니다"를 사용자에게 알린다. **에러로 전체를 막지는 않는다.**
- 따라서 **가능한 한 빠르게**(수백 ms 내) 응답해 달라. 무거운 권한 계산이 필요하면 캐시해도 좋다.

### 주의

- `knoxId` 는 SIREN에 로그인한 **최종 사용자**다. 서비스 계정이 아니다.
- 권한이 없는 사용자에 대해 **403이 아니라 `{"canView": false, "canEdit": false}` 를 200으로**
  돌려 달라. 403은 "SIREN이 이 API를 호출할 자격이 없다"는 뜻으로만 쓴다.

---

## 2. 요청 ②: SIREN의 recipient는 그쪽 권한을 바꾸지 않는다

### 알아둘 것

SIREN 화면에서 어떤 사용자를 그 산출물의 **recipient로 등록**하는 일이 생긴다. 이건
**알림을 받을 대상**이라는 뜻일 뿐이며, **그 서비스의 어떤 권한도 부여하지 않는다.**

- SIREN은 recipient 등록 시 그 서비스에 **어떤 API도 호출하지 않는다.**
- recipient가 그 산출물을 실제로 열 수 있는지는 **전적으로 그 서비스가 판정**한다.
- 반대로, SIREN에서 release 알림을 받은 사람이 링크를 눌러 서비스로 들어갔을 때
  **권한이 없어 막히는 것은 정상 동작**이다. 그 상황을 오류로 취급하지 말아 달라.

### 그래서 서비스가 대응해야 할 수도 있는 것

| 상황 | 권장 대응 |
|---|---|
| SIREN 알림 링크로 들어왔는데 권한이 없다 | "접근 권한이 없습니다 + 권한 요청 경로" 안내 화면. 500이나 빈 화면 금지 |
| 권한 요청 창구가 없다 | 담당자 연락처라도 노출 |

---

## 3. 참고: SIREN 쪽 열람 규칙 (서비스 변경 불필요)

혼동을 막기 위해 적어 둔다. **아래는 SIREN 내부 규칙이며 서비스가 구현할 것은 없다.**

SIREN 화면에서 A Tier 산출물의 상세를 열 수 있는 사람은 이제 다음뿐이다.

```
그 산출물이 놓인 workflow의 Edit 권한자
또는
SIREN에 등록된 그 산출물의 recipient (부서 또는 개인)
```

> 즉 **그 서비스에 view 권한이 있어도, SIREN의 recipient가 아니면 SIREN 화면에서는 안 보인다.**
> 이건 SIREN이 "누가 무엇을 받는지"를 명시적으로 관리하기 위한 규칙이며, 서비스 자신의 화면에는
> 아무 영향이 없다. 그 서비스에서는 원래대로 자기 권한 체계대로 보여주면 된다.

---

## 4. 참고: 필드명 매핑 (서비스 변경 불필요)

SIREN 내부에서 `isReleased` 를 **`isPublished`** 로 개명했다. 산출물 하나가 공식 버전을 확정하는
행위를 `publish`, workflow가 부서에 전달하는 행위를 `release` 로 용어를 분리했기 때문이다.

- **`observer-contract-v1.yaml` 의 필드명은 그대로 `isReleased` 를 유지한다.** 외부 계약이므로
  바꾸지 않는다.
- SIREN 쪽 어댑터에서 `isReleased → isPublished` 로 매핑한다.
- 서비스는 지금처럼 `isReleased` 를 정확히 신고해 주기만 하면 된다.

---

## 5. 향후 예정 (지금 구현 불필요)

- SIREN에서 A Tier 산출물의 recipient를 편집할 수 있는 사람을, 현재는 workflow Edit 권한자로
  두고 있다. 나중에 **`access` 응답의 `canEdit` 가 true인 사람만**으로 좁힐 예정이다.
  요청 ①의 `access` 가 준비되어 있으면 SIREN 쪽 한 줄 수정으로 전환된다.

---

## 6. 체크리스트

- [ ] `GET /artifacts/{id}/access?knoxId=` 구현 (`canView`, `canEdit`, 선택적 `editors`)
- [ ] 권한 없는 사용자에게 403이 아닌 `200 {canView:false, canEdit:false}` 반환
- [ ] 응답 지연을 수백 ms 이내로 (필요하면 캐시)
- [ ] 권한 없는 사용자가 링크로 진입했을 때의 안내 화면 확인
- [ ] `isReleased` 를 계속 정확히 신고하는지 확인
